## 0. 한 줄 요약

교수자와 학생을 잇는 관계가 **저장돼 있지 않다.** `Enrollment` 를 도입해 "누가 내 학생인가"를
사실로 만들고, 그 위에 명단·반별 통계·제적을 얹는다.

---

## 1. 지금 무엇이 없는가 (실코드 확인)

### 1.1 "내 학생"은 저장된 관계가 아니라 사후 파생이다

```
LearningSession.user_id  →  users
LearningSession.lecture_id → lectures.course_id → courses.instructor_id
```

교수자의 학생 목록은 **세션 기록을 거꾸로 타서** 만들어진다. 이 구조의 결과:

| 증상 | 원인 |
|---|---|
| **등록했지만 한 번도 안 본 학생이 존재하지 않는다** | 세션 행이 없으면 어디에도 안 나타난다. "미시청자 3명"을 특정할 수 없다 — 분모가 없기 때문. |
| 출석률의 분모가 "본 사람 수"다 | `dashboard_svc.get_attendance` 는 lecture 단위 세션만 센다. 전체 수강생 대비 비율이 아니다. |
| 학생을 반에서 뺄 방법이 없다 | 뺄 관계 자체가 없다. 세션을 지우면 연구 데이터가 사라진다. |
| 반 단위 집계가 불가능하다 | 집계 단위가 `lecture` 뿐이다. |

### 1.2 접근 제어가 없다

`POST /api/v1/sessions` (`app/api/v1/sessions.py`)는 `require_student` 만 본다.
**`lecture_id` 를 아는 로그인 학생이면 누구나 세션을 시작한다.** 링크가 유출되면 타 학교
학생도 시청·퀴즈·질문이 된다. 지금은 이것이 "강의 링크로 자유 가입"이라는 편의의
뒷면이다.

### 1.3 이미 있는 것 (재구현 금지)

| 요소 | 위치 |
|---|---|
| 교수자 ↔ 강좌 소유 | `courses.instructor_id` |
| 강좌 ↔ 강의 | `lectures.course_id` |
| 강의별 출석·참여 분석 | `/api/v1/dashboard/{lecture_id}/attendance` · `/engagement` |
| 강의별 학습자 화면 | `/professor/learners/[lectureId]` |
| 학생 학번·소속 | `users.student_number` · `users.school` · `users.department` |
| 소유권 가드 | `assert_professor_owns_lecture` |

## 2. 핵심 결정 — 반(class)의 단위는 `Course` 다

`Course` 는 이미 `instructor_id` 를 갖고 `Lecture` 를 묶는다. 여기에 `Enrollment` 를 걸면
**교수자 → 강좌(반) → 학생** 이 한 번에 성립한다.

**`ClassGroup` 을 새로 만들지 않는 이유**: 계층이 `Course → ClassGroup → Lecture` 3단이 되면
강의 소유권 판정, 대시보드 집계, 비용 귀속, 분석 스펙(`analytics-spec.md`)의 집계 단위가
전부 바뀐다. 파급이 기능 가치에 비해 크다.

**분반이 필요하면 `Course` 를 하나 더 만든다** — "중국어문법의 이해 (01분반)",
"(02분반)". 강의 자료는 복제해야 하지만, 베타 규모(교수자 수십 명)에서는 이 비용이
계층 추가보다 싸다. 분반이 실제로 반복 요구가 되면 그때 `Course.parent_id` 로
자기참조를 붙이는 편이 3단 계층보다 안전하다.

> ⚠️ 이 결정은 §9-A 에서 뒤집힐 수 있다. 아래 설계는 `Course = 반` 전제로 쓰였다.

## 3. 데이터 모델

### 3.1 신규 테이블 `enrollments`

```
enrollments
  id            UUID PK
  course_id     UUID FK → courses.id   ON DELETE CASCADE   NOT NULL
  student_id    UUID FK → users.id     ON DELETE CASCADE   NOT NULL
  status        VARCHAR(16) NOT NULL DEFAULT 'active'   -- active | withdrawn
  source        VARCHAR(16) NOT NULL DEFAULT 'link'     -- link | manual | roster
  joined_at     TIMESTAMPTZ NOT NULL DEFAULT now()
  withdrawn_at  TIMESTAMPTZ NULL
  withdrawn_by  UUID FK → users.id ON DELETE SET NULL    -- 제적한 교수자
  note          TEXT NULL                                -- 교수자 메모(제적 사유 등)

  UNIQUE (course_id, student_id)
  INDEX  (course_id, status)          -- 명단 조회 핫패스
  INDEX  (student_id)                 -- "내가 듣는 강좌" 역방향
```

**설계 근거**

- **제적은 행 삭제가 아니라 `status='withdrawn'`.** 삭제하면 이미 쌓인 세션·평가 결과가
  주인 없는 데이터가 되고, 연구 데이터 모델(스펙 10)의 코호트 집계가 과거와 어긋난다.
  제적 이력 자체가 연구 대상이기도 하다(중도 이탈).
- **`UNIQUE(course_id, student_id)`** 때문에 재등록은 새 행이 아니라 기존 행을
  `active` 로 되돌리는 것이다. 등록/제적/재등록이 같은 행의 상태 전이가 되어 이력이
  한 줄에 모인다.
- **`source`** 는 "어떻게 들어왔는가" — 링크 자동 등록인지, 교수자가 손으로 추가했는지,
  사전 명단(CSV)에서 왔는지. 베타 운영 중 "학생이 어떻게 유입되는가"를 볼 수 있고,
  나중에 사전 명단 기능을 붙일 때 구분자가 된다.
- `withdrawn_by` 는 교수자 본인 또는 (드물게) 운영자. 스펙 14 §5 원칙대로 **쓰기에는
  추적이 따라붙어야** 한다.

### 3.2 마이그레이션

새 테이블 1개 + 인덱스 3개. 번호는 착수 시점 head 기준이며, **스펙 14 §C 의 render
triage 가 `0072` 를 예약**하고 있으므로 그 뒤 번호를 쓴다.

## 4. 등록은 언제 생기는가

### 4.1 자동 등록 (기본 경로, `source='link'`)

학생이 강의 링크로 **첫 세션을 시작할 때** 등록이 만들어진다.

```
POST /api/v1/sessions (lecture_id)
  → lecture.course_id 조회
  → enrollments UPSERT (course_id, student_id)
      · 없으면 status='active', source='link' 로 생성
      · status='withdrawn' 이면 → 403 (§4.2)
      · 이미 'active' 면 → 통과 (멱등)
```

**지금 흐름을 깨지 않는 것이 요건이다.** 학생은 여전히 링크만 받으면 들어온다. 승인
대기도, 사전 명단도 없다. 달라지는 건 그 순간 관계가 **기록된다**는 것뿐이다.

> 등록 생성은 세션 시작 트랜잭션 안에서 처리하되, `UNIQUE` 충돌은 정상 경로로 삼는다
> (동시에 두 탭을 열면 충돌한다). `ON CONFLICT DO NOTHING` 후 재조회.

### 4.2 제적자의 재진입

**제적된 학생이 링크로 다시 들어오면 403.** 자동 복구되면 제적이 아무 의미가 없다.
재등록은 교수자가 명단에서 되돌리는 것으로만 가능하다.

학생 화면에는 "이 강좌에서 수강이 종료되었습니다. 담당 교수님께 문의하세요." 를 띄운다
— 로그인 실패나 링크 오류처럼 보이면 학생이 엉뚱한 곳을 헤맨다.

### 4.3 교수자의 수동 추가 (`source='manual'`)

명단 화면에서 학번·이메일로 검색해 추가. **이미 가입한 학생만** 대상이다. 미가입자를
미리 넣는 건 사전 명단(§8-3단계)의 몫이다.

## 5. 접근 제어를 어디까지 조일 것인가

세 단계가 있고, **이번 설계는 1단계를 권장**한다.

| 단계 | 규칙 | 교수자 부담 | 유출 링크 방어 |
|---|---|---|---|
| **1. 열린 등록 + 명시적 제적** (권장) | 링크를 아는 학생은 자동 등록. 제적자만 차단. | 없음 | 사후 대응 |
| 2. 승인제 | 등록 요청 → 교수자 승인 후 시청 | 개강 첫 주에 승인 노동 집중 | 사전 차단 |
| 3. 사전 명단 대조 | CSV 학번 명단에 있는 사람만 등록 | 명단 준비 필요 | 사전 차단 |

**1단계 권장 이유**: 8월 베타의 성패는 교수님이 첫 수업을 굴릴 수 있느냐다. 승인제는
30명 반에서 개강 직후 30번의 클릭을 요구하고, 승인이 늦으면 학생이 수업을 못 듣는다.
링크 유출은 베타 규모에서 실제 위험이라기보다 가능성이며, 제적으로 사후 대응이 된다.

2·3단계는 `enrollments.status` 에 `pending` 을 추가하면 **같은 모델 위에서** 확장된다.
지금 만들지 않을 뿐 길은 막지 않는다.

## 6. 화면

### 6.1 `/professor/courses/[courseId]/roster` — 명단 (신규)

- 표: 이름 · 학번 · 소속 · 등록일 · 최근 활동 · 진도(수강 강의 n개 중 완료 m개) · 상태
- 필터: 활성 / 제적 / **미시청**(등록했지만 세션 0건 — §1.1 이 못 하던 것)
- 행 액션: 제적 / 재등록 / 메모
- 상단 요약: 등록 n명 · 활성 n명 · 미시청 n명

**제적은 확인 대화상자 + 사유 입력(선택).** 되돌릴 수 있음을 문구로 알린다.

### 6.2 기존 학습자 화면과의 관계

`/professor/learners/[lectureId]` 는 **강의 단위**로 남긴다. 명단은 **강좌(반) 단위**다.
둘은 층위가 다르므로 통합하지 않는다. 대신 서로 링크한다.

### 6.3 학생 측

변경 없음. 등록은 학생에게 보이지 않는 배경 동작이다. 유일한 노출은 §4.2 의 제적 안내.

## 7. 반별 통계

`Enrollment` 가 생기면 **분모가 생긴다.** 이게 실질적 가치의 절반이다.

| 지표 | 지금 | Enrollment 이후 |
|---|---|---|
| 출석률 | 세션 있는 학생 기준 | **등록 학생 기준** (안 본 사람이 분모에 든다) |
| 미시청자 | 알 수 없음 | 명단에서 특정 가능 → 개별 독려 |
| 이탈 | 알 수 없음 | 최근 n주 세션 0 → 이탈 위험군 |
| 반 평균 | 강의별만 | 반 단위 롤업(강좌의 모든 강의 가중 평균) |

신규 엔드포인트 `GET /api/v1/courses/{course_id}/roster-stats` — 등록 수, 활성/미시청/이탈
분포, 강의별 완료율. 기존 `dashboard_svc` 패턴(N+1 금지, group by 후 파이썬 조인)을 따른다.

분석 스펙(`analytics-spec.md`)의 4시나리오 판정도 분모가 정확해지면 정밀도가 올라간다 —
"이탈"을 지금은 관측조차 못 한다.

## 8. 단계 분할

| 단계 | 범위 | 규모 |
|---|---|---|
| **1** | `enrollments` 테이블 + 세션 시작 시 자동 등록 + 제적자 403 | 백엔드, 중 |
| **2** | 명단 화면(`/professor/courses/[id]/roster`) + 제적·재등록 | 백+프론트, 중 |
| **3** | 반별 통계 롤업 + 출석률 분모 교체 | 백+프론트, 중 |
| **4** | *(선택)* 사전 명단 CSV 업로드 · 승인제(`pending`) | 대 |

1단계만 끝나도 데이터가 쌓이기 시작한다. **8월 베타 전에 1단계는 넣는 게 좋다** —
관계를 그때부터 기록해야 학기 말에 분석할 데이터가 있다. 2·3단계는 학기 중 추가해도
소급 집계가 된다.

## 9. 열린 질문 (착수 전 결정 필요)

**A. 반의 단위** — `Course` 를 반으로 쓸 것인가(§2), 아니면 분반 개념(`ClassGroup`)을
따로 둘 것인가? 같은 과목을 여러 분반으로 운영하실 계획이면 지금 정해야 한다. 나중에
바꾸면 집계 단위 전체가 흔들린다.

**B. 접근 제어 강도** — §5 의 1단계(열린 등록 + 제적)로 갈 것인가, 처음부터 승인제인가?

**C. 사전 명단** — 학교 수강신청 명단(학번 CSV)을 미리 넣어 두고 대조하는 방식이 필요한가?
필요하면 `users.student_number` 만으로 매칭이 되는지(학번 표기 일관성) 확인이 선행돼야 한다.

## 10. 범위 밖

- **학생 간 상호작용**(조 편성, 토론) — 별건.
- **성적 산출·이의신청** — LMS 영역. ClassAuto 는 학습 데이터를 제공하고 성적은 교수자가
  기존 LMS 에서 낸다.
- **학교 LMS 연동**(LTI, 수강생 자동 동기화) — 기관 계약 단계의 과제.
- **운영자의 반 간섭** — 스펙 14 §5 원칙상 콘솔은 읽기 위주다. 반 관리는 교수자의 것.
